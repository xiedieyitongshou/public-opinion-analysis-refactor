# 数据生命周期与存储策略

## 文档目标

本文定义舆情观察系统 v0.3 的数据生命周期、采集频率、存储分层、事件状态、热度重算范围和清理归档策略。

设计约束：

- 目标服务器可用存储空间约 40G。
- 系统需要每 2-3 小时自动采集分析一次。
- 系统需要记录事件热度走势，但不能无限保存原始数据和高频快照。
- 模式 A 优先，模式 B 后续复用已有数据，不默认永久追踪每个查询主题。

核心原则：

```text
事件摘要长期留
原始数据短期留
高频快照短期留
历史趋势压缩留
低价值事件及时归档或忽略
```

## 存储风险

如果不做生命周期控制，系统会很快遇到以下问题：

- 每 2-3 小时采集一次，多平台数据量持续增长。
- 热点事件几天后失去关注，但仍占用存储和计算资源。
- 事件快照按小时累积，长期会膨胀。
- 草稿简报、工具日志和原始 payload 如果长期保存，会浪费大量空间。
- 模式 B 如果对每个查询都创建长期追踪主题，计算量和采集量会失控。

因此，数据存储不能采用“全部永久保存”的策略。

## 采集频率策略

### 分级调度

不同数据源变化速度不同，不应全部按同一频率采集。

建议频率：

| 来源类型 | 数据源 | 启用条件 | 建议频率 | 单次上限 |
|---|---|---|---:|---:|
| 即时热榜 | 微博热搜 | `use`，采用 RSSHub + CLI 当前链路 | 每 2 小时 | Top 50 |
| 问题热榜 | 知乎热榜 | 仅 `use` / `fallback` 后启用 | 每 3-4 小时 | Top 50 |
| 视频热门 | B站热门 / 排行榜 | 后续候选 | 每 6 小时 | Top 50 |
| 新闻源 | 人民网 | `use` | 每 4-6 小时 | 50-100 条 |
| 新闻源 | 中国新闻网 | `use` | 每 4-6 小时 | 50-100 条 |
| 新闻源 | 新华网 | `fallback` | 每 4-6 小时 | 50-100 条 |
| 新闻源 | 央视网 | 后续候选 | 每 6 小时 | 50 条 |

第一阶段可以先使用统一调度：

```text
每 3 小时运行一次自动采集分析
每个来源最多采集 50 条
```

后续再按平台变化速度拆分频率。

### 采集边界

第一阶段只采集：

- 热榜页。
- 新闻列表页。
- RSS 或等价公开列表。
- 栏目首页。

第一阶段不采集：

- 大规模评论。
- 转发链路。
- 用户主页。
- 视频弹幕全文。
- 需要登录态的个性化推荐流。
- 深度历史翻页。

## 存储分层

系统数据分为 7 层：

| 层级 | 示例 | 用途 | 保留策略 |
|---|---|---|---|
| 原始采集数据 | `raw_payload` | 调试、字段追溯 | 短期 |
| 标准化条目 | `items` | 事件抽取、来源引用 | 中短期 |
| 事件主表 | `events` | 事件实体、长期索引 | 长期轻量 |
| 平台评分 | `platform_scores` | 平台热度对比 | 中期 |
| 事件快照 | `event_snapshots` | 走势判断 | 高频短期，低频中期 |
| 简报草稿 | `draft reports` | 人工发布前确认 | 短期 |
| 正式日报 | `published daily_reports` | 历史产出展示 | 长期 |
| 语义索引 | `event_embeddings` / `semantic_fingerprint` | 事件匹配 rerank 和模式 B 后续检索预留 | 跟随 items / events 生命周期 |
| 工具日志 | `agent_tool_calls` | 可观测性和排障 | 短期 |

## 保留周期

40G 服务器下建议默认保留周期：

| 数据 | 保留周期 | 说明 |
|---|---:|---|
| `raw_payload` / 原始采集数据 | 3-7 天 | 只用于排障，不长期保存 |
| `items` / 标准化条目 | 14-30 天 | 支撑短期事件检索和来源引用 |
| `events` / 活跃事件 | 活跃期保留 | 参与热度计算 |
| `events` / 归档事件 | 长期轻量保留 | 只保留摘要和统计 |
| `platform_scores` | 30 天 | 支撑近期平台热度分析 |
| `event_snapshots` 高频快照 | 7 天 | 保存每 2-3 小时走势 |
| `event_snapshots` 日级压缩快照 | 30-90 天 | 保存每日 max / avg / last |
| `draft reports` / 自动草稿 | 3-7 天 | 只保留近期待确认草稿 |
| `published daily_reports` / 正式日报 | 长期 | 项目展示和历史回顾 |
| `event_embeddings` / 语义向量 | 跟随 `items` 或活跃 `events` | 只保存向量 ID、模型、生成时间和必要索引，不长期保留无引用向量 |
| `agent_tool_calls` / 工具日志 | 7-14 天 | 排障和观测 |
| `evaluation_runs` | 30-90 天 | 质量趋势观察 |

长期保留不等于全量保留。归档事件只保留轻量字段，不保留完整原始数据。

embedding 和语义索引是派生数据，不是事实来源。删除原始条目或归档事件时，应同步清理无引用向量；公开日报只保留匹配解释和来源引用，不暴露完整向量。

## 事件生命周期

事件建议使用以下状态：

```text
active
cooling
archived
ignored
```

### active

含义：

- 事件仍在活跃传播。
- 近 48 小时内有新增来源、热度上升或仍处于高分区间。

处理：

- 参与每轮热度重算。
- 保留较完整的来源引用。
- 可进入草稿简报候选。

### cooling

含义：

- 事件热度开始下降，但仍有短期观察价值。
- 近 48 小时无明显新增，但此前热度较高。

处理：

- 降低重算频率。
- 只在有新增来源或分数明显变化时更新。
- 可作为“降温事件”或历史对照。

### archived

含义：

- 事件已不再活跃。
- 通常 7 天无新增且热度低于阈值。

处理：

- 不参与每轮热度重算。
- 只保留轻量摘要和统计。
- 高频快照压缩或清理。

长期保留字段建议：

```text
event_id
title
summary
domain
first_seen_at
last_seen_at
status
peak_score
last_score
source_count
platform_count
primary_sources
archive_reason
```

### ignored

含义：

- 低质量、重复、误合并、无效或明显不适合进入简报的事件。

处理：

- 不参与热度重算。
- 不进入简报。
- 可短期保留原因，用于 Evaluation 和规则优化。

## 事件状态流转

建议状态流转：

```text
new signal
-> active
-> cooling
-> archived
```

异常流转：

```text
new signal
-> ignored
```

典型规则：

- 新事件默认进入 `active`。
- 近 48 小时无新增且热度下降，进入 `cooling`。
- 7 天无新增且分数低于阈值，进入 `archived`。
- 明显重复、低质量或误识别，进入 `ignored`。
- 人工标记关注的事件可延长 `active` 或 `cooling` 周期。

## 热度重算范围

每轮自动分析不能对所有历史事件重新计算热度。

每轮只计算：

- 最近 24-72 小时出现过的事件。
- 当前 `active` 事件。
- 高热但仍处于 `cooling` 的事件。
- 本轮新采集条目关联的事件。
- 人工标记关注的事件。

不参与每轮重算：

- `archived` 事件。
- `ignored` 事件。
- 长期无新增的低热事件。
- 只保留历史展示价值的旧事件。

如果后续模式 B 查询归档事件，只返回历史摘要和已有快照，不触发默认重算。

## 快照策略

`event_snapshots` 用于记录走势，但不能无限按小时保存。

建议：

```text
近 7 天：保留每 2-3 小时高频快照
7-30 天：压缩为每日 max / avg / last
30-90 天：只保留每日 last 或 peak
90 天后：按事件重要性决定是否保留
```

日级压缩字段建议：

```text
event_id
snapshot_date
max_score
avg_score
last_score
peak_platform
source_count
platform_count
trend_status
compressed_from_count
```

压缩完成后，可以删除对应日期的高频快照。

## 草稿与正式日报

自动采集分析链路每 2-3 小时生成草稿快照，但草稿不应长期保存。

建议：

- 自动草稿保留 3-7 天。
- 被阻断草稿保留 7-14 天，用于排障。
- 正式发布日报长期保留。
- 正式日报只保留最终结构化结果和来源摘要，不嵌入完整原始 payload。

草稿状态：

```text
draft
draft_ready_for_review
draft_needs_review
draft_blocked_for_publish
```

正式发布状态：

```text
published
published_with_warning
blocked
```

## 原始数据清理

`raw_payload` 只用于短期调试和字段追溯。

清理规则：

- 超过 3-7 天的 `raw_payload` 删除或置空。
- 已成功标准化且无异常的 `raw_payload` 可以更早删除。
- `quality_flags`、`source_citation` 和必要字段保留在 `items` 或 `events` 中。
- 不长期保存完整 HTML、评论全文、视频内容或大体积媒体资源。

## 工具日志清理

`agent_tool_calls` 用于观测和排障，但不应永久保留详细输入输出。

建议：

- 详细工具日志保留 7-14 天。
- 超期后只保留聚合统计。
- 大字段输入输出摘要化。
- 错误样例可脱敏后进入 Evaluation cases。

长期聚合字段建议：

```text
date
tool_name
source_id
success_count
failure_count
retry_count
avg_latency_ms
error_type_summary
```

## 模式 B 的存储边界

模式 B 后续不能默认把每个用户查询变成永久追踪主题。

建议规则：

- 默认只检索已有 `items`、`events`、`platform_scores` 和 `event_snapshots`。
- 查询结果不足时提示“当前数据源未覆盖或证据不足”。
- 只有人工关注或显式订阅的主题才允许定向采集。
- 定向采集必须有 TTL。
- 过期主题自动停止采集和热度重算。

主题追踪状态可以后续扩展为：

```text
one_time_query
watching
paused
expired
archived
```

v0.3 只保留模式 B 占位入口，不实现主题追踪。

## 数据库增长监控

系统应定期记录存储占用。

建议指标：

- 数据库文件大小。
- `items` 数量。
- `events` 数量。
- `event_snapshots` 数量。
- `daily_reports` 数量。
- `agent_tool_calls` 数量。
- 每日新增数据量。
- 清理任务删除数量。
- 快照压缩数量。

告警阈值建议：

```text
数据库超过 20G：进入 warning
数据库超过 30G：缩短 raw_payload 和 tool logs 保留周期
数据库超过 35G：暂停非关键数据源采集，执行强制清理
数据库超过 38G：只保留核心采集和正式日报，阻断草稿快照生成
```

## 清理任务

建议配置每日清理任务：

```text
删除过期 raw_payload
删除过期 draft reports
删除过期详细 tool logs
压缩 7 天前 event_snapshots
归档低热且无新增事件
清理 ignored 事件的冗余数据
记录清理结果
```

清理任务失败不应删除未知数据，但必须记录错误并在 Agent Ops 面板展示。

## 第一阶段默认配置

v0.3 推荐默认配置：

```text
自动采集分析频率：每 3 小时
每源单次采集上限：50 条
raw_payload 保留：3 天
items 保留：14 天
高频 event_snapshots 保留：7 天
日级压缩快照保留：90 天
自动草稿保留：7 天
正式日报保留：长期
详细 tool logs 保留：7 天
active -> cooling：48 小时无新增且热度下降
cooling -> archived：7 天无新增且低于热度阈值
```

这些默认值应放入配置文件，后续根据真实运行数据调整。

## 对后续实现的影响

第 2 周业务数据模型需要支持：

- 事件状态字段。
- 快照压缩字段。
- 草稿状态字段。
- 数据清理时间字段。
- 数据源采集频率配置。
- 工具日志摘要字段。

第 6 周评分逻辑需要支持：

- 只重算活跃事件。
- 对归档事件跳过评分。
- 历史快照不足时降级为 `unknown` 或 `new`。

第 8 周部署与稳定性观察需要支持：

- 数据库增长监控。
- 定时清理任务。
- 快照压缩任务。
- 存储阈值告警。

## 结论

40G 存储空间足够支撑 v0.3 MVP，但前提是系统从第一阶段就采用生命周期策略：

- 不永久保存原始数据。
- 不永久保存高频快照。
- 不对所有历史事件反复计算热度。
- 不让模式 B 的每次查询变成永久追踪任务。
- 只长期保留轻量事件摘要、正式日报和压缩后的趋势数据。
