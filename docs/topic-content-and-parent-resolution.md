# 话题正文、来源摘要与父话题归并

更新日期：2026-10-23。返回[项目 README](../README.md)。

## 微博匹配不再仅依赖标题

RSS 热搜标题仍是发现入口。已采集 CLI 样本中，只有关联判定为 accepted、非 audit_only 且可定位出处的正文可以补强匹配。优先使用 HTTP(S) 原文链接；链接缺失时，用有效数字 external_id 或 mid 构造 `https://m.weibo.cn/detail/{id}`。详情链接不代表已联网验证可访问，原文删除或访问限制仍可能影响打开。既无链接也无有效 ID 的样本仍不用于正文补强。清理 HTML、链接和重复查询 hashtag，去重后最多选取 3 条，每条最多 360 字。新 EventSignal 与已有候选事件均带入这些上下文，供 BM25、embedding 和 reranker 使用；正文与出处同时保存在来源信号中。

### 2026-10-23：修复缺少 URL 时正文被跳过

原来的链接门槛用于保证摘要出处可追溯，但未兼容 CLI 返回微博 ID、URL 为空的实际数据，导致已接纳正文被跳过。现改为在共享正文选取层解析出处，使新采集和已保存的历史样本同时受益，不需要重新付费搜索。相关性、audit_only、正文长度和去重条件保持不变；热度公式不变。历史简报和已保存的匹配决定不会自动重写，需重新生成简报或另行回放匹配。针对性测试覆盖无 URL 的匹配两侧上下文、摘要引用、无效 ID 排除及审核样本排除。

后续离线复核发现两项未解决边界：正文高分仍可能对应不同具体事件；当前 CLI 放行条件只检查一侧有有效 CLI 正文，未明确限制另一侧必须是知乎／微博，因此也可能影响微博与官媒的关系。详见[归并复核报告](../reports/cli-context-rematch-audit-2026-10-23.md)。知乎与官媒的旧误匹配不能作为微博正文修复是否有效的对照；官媒已有 RSS 描述／搜索片段参与匹配，原文全文补强和平台规则调整尚未实施。

不新增搜索请求，不调用生成式 LLM，不因正文增加而直接放宽自动合并阈值。已有身份、时间、实体及动作冲突检查仍有效。已接纳样本也可能含有误判或网友观点，因此正文是匹配依据，不是事实真实性证明。短标题没有可用 CLI 正文时仍保留原标题。

### 高分正文自动合并（2026-10-22）

新增正文放行路径：reranker ≥ 0.95、至少一侧带有来自已接纳 CLI 样本的有效正文，且两侧均有足够文本、没有明确冲突或模型异常时，不再要求标题至少 8 字或必须提取出实体。纯标题仍使用原有标题匹配条件。无来源证明的任意摘要不触发这一放行路径；只剩模糊短标题的对侧也不能触发。

正文侧至少 12 个有效字符；另一侧须有至少 8 字标题或 24 字描述。这些长度只是最低信息量检查，不代表事实可信度。候选侧优先保留 CLI 正文，避免被历史描述挤出匹配文本。达到相近高分的多个候选仍进入人工审核。

实体列表不相交不再直接判为冲突。明确主体冲突要求同类实体且能在各自文本中找到依据；型号、地点、动作及明确日期等已有规则继续生效。CLI 正文首句也参与有限的明确事实冲突检查。这些是保守规则，并非完整语义矛盾识别；未检出冲突不等于已证实同一事件。直接事实冲突优先否定候选，只有事件内部的证据歧义才继续转人工。

新规则用于下一次匹配，不根据历史保存的高分直接批量合并旧审核任务，也不修改已确认的审核结论。

验证：新增 10 项高分正文边界用例，完整离线回归 416 项通过。覆盖正文位于任一侧、实体缺失／不相交、正文缺失、分数不足、模型异常、明确型号冲突及多个高分候选；没有新增付费采集。真实审核减少比例仍需后续运行统计。

## 独立话题与增强数据分别处理

- 有效热榜发现信号没有可接受归并目标时，可以独立保留，包括“荣耀”等短标题；不再要求至少 4 个字。“热议”“热搜”“热点”这类只有泛称的线索仍需核查。
- 搜索增强不能独立创建热点。父话题人工审核后，系统查找等待父话题的审核记录：已接纳、同一知乎问题 ID 的回答可回挂到父话题最终所属事件，同时关闭该增强记录的待审状态并记录触发审核 ID。
- 被拒绝的关系、其他问题 ID、已经属于另一事件的数据都不会自动迁移。微博查询词没有知乎问题 ID 的强身份效力，不凭查询词自动执行历史回挂。
- 没有当前候选目标的审核卡不再把历史检索分数当作当前归并分数展示。真正存在候选冲突或竞争目标的情况仍保留审核。

父话题回挂与人工决定在同一数据库事务中保存，随后沿用既有审核后简报重算流程。旧的已完成审核不会因代码更新自动重新执行；历史遗留任务需要单独重算或处理。

## 来源摘要与共同关注

知乎优先摘录热榜条目的问题描述，没有描述则显示问题标题，不把搜索回答冒充问题描述。微博复用上述正文选取结果，最多展示两段、每段 200 字，并附摘要原文链接。官媒有描述时显示报道摘录；没有足够正文时明确提示信息不足。

来源摘录保存在 `EventCard.source_summary`，与 `summary` 中的系统来源说明分开；它是有标注的摘录，不是 LLM 综合判断。摘要只从当前简报已接纳的引用条目生成，不能从事件历史成员中任意取正文。“此前报道”说明继续保留。

知乎与微博均有已接纳热榜话题的事件，先展示在“跨平台共同关注”栏目，同一事件在该栏目只出现一次。各平台栏目仍保留它，方便查看各自的排序和热度趋势；不相加、不比较两个平台的热度。栏目按事件来源判断，不把 A/B/C 字母顺序误当作跨平台热度。

知乎卡片同时展示榜位和站内热度，分数沿用后端 0–1 量纲、保留三位小数，并标注“系统计算，仅限知乎内比较”。缺失时显示“暂不可用”，真实零分正常显示；排序与热度计算公式不变。网页、HTML 邮件和纯文本简报共用此展示规则。

## 验证与使用

针对性测试见 `backend/tests/test_topic_content.py`，覆盖过滤与去重、匹配两侧上下文、摘要来源、短标题边界、同问题回挂、拒绝关系和其他事件所有权保护。简报回归还检查跨平台栏目及 HTML／纯文本渲染。

本次离线回归共 406 项通过（容器临时目录缺少样例路径的 5 项补齐路径后重跑通过）。使用现有 10 月 21 日采集窗口只读生成预览，得到 240 个事件，169 个有摘要原文依据，3 个跨平台共同关注事件，简报质量检查通过；未新增采集或发送邮件。

服务加载新代码后，新采集及新生成的简报使用这些规则；已保存简报是版本快照，不会被静默覆盖。可以从后台用已有数据重新生成简报来查看摘要，无需重新付费采集，也不会自动发送邮件。
