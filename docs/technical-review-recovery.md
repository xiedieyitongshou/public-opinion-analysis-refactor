# 技术异常复核的自动收尾

2026-11-02

## 解决的问题

前一轮的 LLM 请求可能因网络、JSON 格式或原文引用校验失败而产生待审任务；后一轮已经成功建立独立话题或归并到事件时，旧任务仍可能留在队列。现在以**最终有效处理结果**为准，自动收尾已被后续成功结果覆盖的技术任务。

不需要归并、但已经通过校验并成功建立独立话题的，同样属于处理成功。人工审核保留给最终仍无法确定归属或能否独立保留、存在真实竞争候选或明确冲突的情况。

## 自动收尾条件

以下条件同时满足才自动处理：

1. 原任务仍待审，属于事件归并的技术错误，如 `llm_unverifiable_evidence`、`llm_invalid_response`、网络失败或超时；没有人工决定，也没有真实的语义疑点或明确冲突。
2. 后续最终结果为 `create` 或 `merge`，已经通过对应模式的校验，未要求复核、未禁止自动分析、未被规则阻止。
3. 结果确实保存到活动事件，相关来源记录当前归属与结果一致。只有模型返回“成功”或来源已有归属，不能单独作为恢复依据。
4. 是同一来源话题：来源记录 ID 对应，或知乎问题 ID、微博规范化话题等稳定身份一致。普通同名标题不能证明同一话题。
5. 成功结果覆盖原任务所有已记录的失败轮次。历史回放按原采集窗口比较，不按回放执行日计算；同一窗口重试还需后续尝试的证据。微博弱话题身份保留自首次失败观测起的24小时限制。

已处理的人工作业、实体／时间等冲突、实质性竞争候选及真实不确定关系，不会因此自动取消。历史证据里保留了语义疑点的任务也继续保留。

## 保存与显示

- 自动归并和独立建事件都在保存归属的同一事务中收尾旧技术任务，失败回滚时两者一起回滚。
- 人工接受归并或独立建事件，也会处理相关旧技术任务。批量操作中用户已勾选的任务保留各自人工决定，不被提前收尾。
- 旧任务保留，状态使用现有 `cancelled`，决定标记为 `auto_recovered`，执行者为 `system:later-success`，不会伪装成人工批准。
- `payload.automatic_recovery` 记录成功的轮次、事件、动作、来源、采集窗口及执行时间；原错误、引用和证据历史保留。
- 任务退出按简报筛选的待审队列。历史简报正文保持快照，生成更正版后才更新正文中的待审数量。
- 不把旧的未归属原始记录强制移入新事件，不修改既有热度观测，不清除历史错误日志，也不额外调用 LLM、微博 CLI 或发送邮件。

## 现有数据修复

`recover_saved_technical_reviews(db, dry_run=True)` 从已保存的归并输出和当前归属核对可恢复任务，默认只预演；指定 `dry_run=False` 后仍由调用者负责事务提交。此工具不会重新采集或请求模型。

修复前备份当前数据库，先核对预演中的成功输出、来源身份与当前归属，再显式提交。没有有效后续结果的继续待审；需要更新正文待审数量时生成更正版，保留原简报。具体任务ID、修复审计、备份与实验结果保存在本机私有数据目录，不纳入版本库。
