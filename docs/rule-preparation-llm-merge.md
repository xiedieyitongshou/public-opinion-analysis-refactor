# 规则准备与 LLM 事件归并

[返回 README](../README.md) · [DeepSeek 配置](llm-reasoning.md) · [缓存与断点](llm-efficiency-and-checkpoints.md)

## 修改方案（2026-11-03）

事件抽取和微博 CLI 相关性可分别选择原规则或 LLM，事件归并继续由总模式控制。规则准备方案可去掉相应阶段的 LLM 请求，同时保留原文供事件比较；也支持只将抽取切回规则、CLI 相关性继续使用 LLM。没有调整 CLI 的热门排序、返回条数、规则相关性阈值或热度公式。

| 阶段 | 当前配置下的处理方式 |
| --- | --- |
| 微博 CLI 与热搜相关性 | 阶段选择 `rules` 时使用原正文预处理、明确冲突检查、正文 reranker 和原阈值；选择 `llm` 时由 LLM 判断并核对引用。待定记录只保留审计 |
| 知乎／微博特征抽取 | 原词典、正则和规则，提取实体、关键词、动作、事件类型及语义指纹文本 |
| 来源身份复用及候选召回 | 原唯一 ID／URL 复用；BM25＋embedding 排名融合，普通候选最多20个 |
| 同平台／跨平台归并 | LLM 分批比较原文，保留双方引用、Schema 和互斥归属检查；最多2个请求并发 |
| 官媒 F 类与补证 | 继续独立规则流程，不调用 LLM |
| 热度与趋势 | 每轮重新记录榜单和已接纳样本的互动指标，不因复用事件归属跳过观测 |

规则特征主要来自标题及已有平台字段，不能替代完整的正文事实抽取。LLM 归并仍看到知乎描述和已接纳的微博 CLI 正文，而不是只看到规则实体或短标题。正文整理沿用此前的数量、长度和去重约束；没有新增 LLM 摘要请求。

原规则曾将来源发布时间填入 `event_time_hint`。在规则抽取供 LLM 归并使用时，该字段明确置空，避免将发布时间误作发生时间；原发布时间仍保存在来源材料中。原纯规则模式的行为保持不变。

## 配置

规则抽取、LLM 判断 CLI 相关性及归并的组合，在实际容器读取的私有环境文件中设置：

```dotenv
EVENT_REASONING_MODE=llm
EVENT_EXTRACTION_MODE=rules
WEIBO_CLI_RELEVANCE_MODE=llm
```

`EVENT_REASONING_MODE` 继续选择事件归并后端。两个阶段开关支持 `inherit|rules|llm`，未配置时默认为 `inherit`，跟随总开关，兼容原部署。示例环境文件显式采用 `rules`；现有私有环境文件不会被模板自动覆盖。

- 完整旧规则链路：总开关及两个阶段均设为 `rules`，或总开关为 `rules`、阶段设为 `inherit`。
- 恢复完整 LLM 链路：总开关为 `llm`，两个阶段设为 `llm` 或 `inherit`。
- 规则抽取、LLM 相关性与归并：使用上面的三行配置。
- 两个准备阶段都走规则、归并走 LLM：在上述基础上将 `WEIBO_CLI_RELEVANCE_MODE` 改为 `rules`。这是此前规则 CLI 回放采用的组合；减少请求不代表接纳质量一定更好。

更改 `env_file` 后，等待活动任务结束，再按当前部署使用的全部 Compose 文件重新创建 backend；仅 `docker restart` 不重新加载环境文件。可只打印非敏感的有效模式确认：

```powershell
docker exec opinion-resource-test-backend-1 python -c "from app.services.llm_client import reasoning_mode,extraction_mode,weibo_relevance_mode; print(reasoning_mode(),extraction_mode(),weibo_relevance_mode())"
```

上面三行配置的预期输出为 `llm rules llm`；两个准备阶段都走规则时为 `llm rules rules`。每个新分析任务保存阶段开关；审核刷新使用原任务保存的模式。没有阶段字段的历史任务按原总模式刷新，避免用新配置隐式改写旧语义。

这是明确选择每阶段的后端，没有失败后自动混用。LLM 归并失败仍保留错误和断点，不用规则分数替它判定合并。阶段模式进入检查点版本，CLI 相关性后端进入来源采样签名，避免跨不同口径复用。

## 验证方法与边界

离线测试覆盖规则特征及正文保留、CLI 原阈值与冲突拒绝、模式上下文恢复、排队任务快照及检查点隔离；断言规则准备不会调用 LLM 抽取或相关性接口。真实回放还需要核对总耗时、每阶段请求／token、待审核错误和合并语义，不能只凭请求数减少判断质量提升。

历史回放使用10月31日第1～4轮原始材料，在独立数据库与缓存内顺序处理；从保存的 CLI 样本重新计算相关性，不沿用旧的接纳结论。不重新获取来源，不发邮件，不覆盖当前页面的数据。失败轮次可能缺少业务窗口字段，因此按原任务轮次 ID 选择材料，不按空缺时间列排序。运行保护、预算和实际结果保存在本机实验报告中，不随实验数据发布。

切回本地 reranker 会增加本地模型加载与推理开销；减少 API 请求不等于保证每轮总耗时降低。不同轮次或不同冷热缓存的总量不能直接用于计算加速比例。规则接纳质量与 LLM 归并质量需分别核对。
