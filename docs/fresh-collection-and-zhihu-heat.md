## 知乎搜索回答接入主热度（历史方案，2026-10-30起默认封存）

当前 Docker 使用[知乎原生热度方案](zhihu-native-heat-and-search-archive.md)，下述搜索互动只在显式启用旧模式时生效，不叠加到原生热度。

此前热榜和搜索分别保存评分，简报优先使用热榜观测，所以回答互动没有进入热榜事件的展示分数。现在在热榜观测评分前，汇总同一次采集返回、相关性已接纳且问题 ID 相同的回答点赞数与评论数。仅使用明确的知乎问题／回答链接，待审、拒绝、其他问题和其他轮次不纳入。

同一回答的重复命中只计一次（重复记录中的指标取最大有效值），不同回答的有效指标相加；这是已采样回答的互动量，不是整个问题的总互动量。多个问题即使已合并为一个事件，也先分别按问题计算，沿用现有事件内聚合规则。跨轮不累计回答总数。

公式权重保持不变：排名50%、快照出现20%、排名变化15%、互动15%。互动项为点赞与评论之和的对数归一化；缺失仍为缺失，可用项重新归一化，不填假零。当前搜索有查询预算，因此未增强的话题仍可能没有互动项。本次没有扩大搜索预算，也没有改变历史快照／排名变化字段的供给方式。

主观测保存回答引用；知乎主评分版本升级，搜索采样配置参与可比性签名，避免新旧评分规则直接比较。历史简报不会自动重写。

## 备份后独立采集

后台“采集任务”新增“备份旧数据后独立采集”选项，默认不勾选。选择时长、间隔及结束动作后，勾选并点击开始，页面再次提示清理范围。要自动生成简报，结束动作选择“生成本次运行简报”；此模式强制使用本次运行范围，不发送邮件。

流程：

1. 检查没有正在运行的采集，且常规定时采集和自动邮件任务关闭；执行现有 CLI 启动检查（会消耗一次调用）。
2. 对文件型 SQLite 数据库取得写锁，重新检查活动采集及待发送邮件。
3. 用 SQLite 在线备份接口复制完整数据库（包含已提交的 WAL 内容），执行完整性校验，成功后才生成正式 `.db` 备份。
4. 在同一事务内清理旧业务数据并创建新采集任务。失败回滚旧数据；备份失败不会清理数据。

清理范围包括采集任务、事件、条目、平台评分与快照、归并审核及其结论、官媒查询、简报和投递记录。因此新事件归并、审核结论、趋势和简报不会继承旧业务数据。

保留数据源配置、邮件设置、收件人、接口调用与额度记录、评估记录。保留调用记录便于核对总费用，不意味着旧数据参与新简报。语义模型缓存仅保存文本计算结果，不保存业务归并结论，继续复用。

## 备份位置与恢复边界

备份位于当前数据库所在目录的 `backups/` 下，命名为 `before-fresh-UTC时间-随机串.db`。Docker 使用 `/app/data/…db` 时，对应 `/app/data/backups/`，通过原数据目录挂载持久保存。页面显示本次备份文件名。失败遗留的 `.partial` 文件不是已验证备份。

备份包含私有业务数据及加密邮件配置，不应提交 Git 或公开分享。当前只支持文件型 SQLite；不自动删除旧备份，需关注磁盘空间。它不备份容器、环境文件、CLI 授权或模型文件。

当前不提供在线恢复按钮。需要恢复时，先停止后端，保留当前数据库及其 WAL/SHM 文件，再将备份作为独立数据库文件配置到 `DATABASE_URL` 后启动。恢复加密邮件密码还需要原有邮件加密密钥。旧页面应关闭并刷新，新库中的数字 ID 可能重新分配，旧简报链接不作为历史访问入口。
