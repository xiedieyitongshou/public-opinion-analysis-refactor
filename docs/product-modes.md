# 产品模式设计

## 文档目标

本文定义舆情观察系统第一阶段的两种产品模式：

- 模式 A：一图流热点简报。
- 模式 B：指定事件搜索。

两种模式面向不同使用场景，但共享同一套数据底座、事件模型、评分逻辑、来源证据和质量约束。

v0.3 的产品策略是优先完整交付模式 A，并为模式 B 预留最小入口和可复用接口。模式 B 的完整能力作为后续版本扩展，不在 v0.3 中完整实现复杂 RAG、向量数据库或多轮自主搜索 agent。

## 产品定位

本系统不是通用搜索引擎，也不是完全自主的信息采集 agent。它更接近一个 workflow-driven agent system：

```text
确定性工作流负责采集、清洗、入库、评分和状态流转
LLM 负责结构化判断、摘要、解释和质量检查
Tool Calling 负责连接确定性业务能力
Guardrails 负责阻止低置信度和高风险输出
Evaluation 负责衡量系统链路是否有效
```

第一阶段的核心目标是把多来源内容稳定转化为可解释、可追踪、可评估的热点事件简报。

## 模式 A：一图流热点简报

### 核心问题

模式 A 回答的问题是：

```text
在默认平台和默认领域下，今天有哪些事件值得关注？
```

它适合以下场景：

- 每日热点简报。
- Web 首页。
- 长图输出。
- 定时推送。
- 面试或项目展示中的完整业务链路演示。

### 输入

模式 A 不要求用户指定具体事件，而是通过系统配置控制观察范围。

默认输入包括：

- `platforms`：默认平台列表。
- `domains`：默认领域列表。
- `keywords`：可选关注关键词。
- `time_window`：默认近 24 小时。
- `max_events`：单次简报最多展示的事件数量。

第一阶段建议将平台和领域作为配置项处理，而不是在前端过早做复杂自定义能力。后续如果数据源质量稳定，再扩展为用户可配置的平台、领域或关键词。

### 输出

模式 A 输出结构化热点简报，并可进一步渲染为首页或长图。

核心输出字段包括：

- `report_date`：简报日期。
- `summary`：当日总览。
- `sections`：按领域、平台或走势划分的栏目。
- `event_cards`：热点事件卡片。
- `source_citations`：来源引用。
- `risk_notes`：风险与不确定性提示。

事件卡片建议包含：

- 事件标题。
- 所属领域。
- 主要平台。
- 综合热度分。
- 平台热度分布。
- 走势状态。
- 一句话摘要。
- 代表性来源。
- 置信度与不确定性提示。

### 展示结构

一图流热点简报建议采用以下栏目：

```text
今日总览
重点事件
分领域热点
分平台热点
正在升温事件
风险与不确定性提示
来源说明
```

栏目不是固定死的 UI 结构，而是 Briefing Agent 的结构化输出目标。前端首页和长图渲染可以基于同一份 `DailyBriefing` 数据生成不同展示形态。

### v0.3 交付边界

v0.3 需要完整交付：

- 自动采集默认来源。
- 标准化内容。
- 抽取并合并事件。
- 计算事件热度。
- 生成结构化热点简报。
- 通过 Guardrails 检查低置信度和来源问题。
- 展示首页 MVP。
- 导出一图流长图 MVP。
- 记录工具调用、任务状态和评估结果。

v0.3 不追求：

- 精确预测未来热度。
- 全平台覆盖。
- 大规模评论全文分析。
- 深度反爬平台采集。
- 复杂个性化推荐。

## 模式 B：指定事件搜索

### 核心问题

模式 B 回答的问题是：

```text
给定一个事件或话题，系统已有数据中有哪些相关证据？不同平台热度如何？
```

它适合以下场景：

- 用户主动查询某个事件。
- 查看某个话题在不同平台的热度差异。
- 回溯事件时间线。
- 检查系统是否已经覆盖某个事件。

### 输入

模式 B 的输入来自用户查询。

核心字段包括：

- `query`：用户输入的事件、话题或关键词。
- `platforms`：默认平台或用户指定平台。
- `time_window`：默认近 7 天，可扩展为近 30 天。
- `domains`：可选领域过滤。
- `include_weak_matches`：是否返回弱匹配候选。

### 输出

模式 B 输出事件检索结果，而不是直接生成确定性结论。

核心输出字段包括：

- `matched_events`：匹配到的已有事件。
- `related_items`：相关原始内容。
- `platform_heat`：不同平台热度快照。
- `timeline`：事件时间线。
- `source_citations`：来源引用。
- `confidence`：匹配置信度。
- `limitations`：证据不足或数据覆盖不足说明。

### v0.3 最小入口

v0.3 只保留模式 B 的最小占位能力：

```text
用户输入事件
-> 保存 event_query
-> 调用 search_existing_evidence 占位工具
-> 检索已有 items / events / event_snapshots
-> 返回已有相关事件、来源列表和热度快照
```

该阶段不做：

- 实时全网搜索。
- 复杂 RAG。
- embedding 检索。
- 向量数据库。
- 多轮自主搜索 agent。
- 证据不足时的自动深度采集。

### 降级策略

模式 B 必须明确处理证据不足的情况。

建议输出分为三类：

- 强匹配：返回事件热度、平台分布、时间线和来源证据。
- 弱匹配：返回候选事件，并提示需要人工确认或更多证据。
- 无匹配：返回“当前数据源未覆盖或证据不足”，不强行生成结论。

## 两种模式的复用关系

模式 A 和模式 B 不应拆成两套系统。它们共享同一套底层链路：

```text
数据采集
-> 标准化内容
-> 事件抽取
-> 事件合并
-> 热度评分
-> 走势快照
-> 来源证据
-> 结构化输出
-> Guardrails
-> Evaluation
```

核心复用对象包括：

- `sources`：数据源定义。
- `items`：标准化内容。
- `events`：事件实体。
- `platform_scores`：平台热度评分。
- `event_snapshots`：事件走势快照。
- `daily_reports`：每日简报。
- `event_queries`：指定事件查询记录。
- `source_citations`：来源引用结构。
- `retrieved_evidence`：检索证据结构。

核心复用工具包括：

- `fetch_source_items`
- `normalize_raw_item`
- `extract_event_signal`
- `match_event`
- `calculate_event_score`
- `generate_daily_briefing`
- `run_report_guardrails`
- `create_human_review_task`
- `run_evaluation_suite`
- `search_existing_evidence`

其中 `search_existing_evidence` 在 v0.3 中只作为占位工具注册，后续用于扩展模式 B。

## 默认平台、领域与关键词

### 平台配置

第一阶段平台配置应遵循稳定优先原则。

平台选择标准包括：

- 可稳定获取标题、链接、发布时间等基础字段。
- 至少能提供排名、报道数量或基础互动指标之一。
- 来源链接可追踪。
- 采集方式适合公开项目展示。
- 不依赖敏感账号、Cookie 或私有接口。

第一阶段建议采用：

- 若干新闻 / 官媒源。
- 若干社区 / BBS 热点源。

具体平台名单应在 `docs/data-sources.md` 中单独说明。敏感的平台限制、失败记录和接口细节不进入公开文档。

### 领域配置

默认领域建议包括：

- 社会。
- 财经。
- 科技。
- 文娱。
- 体育。
- 国际。

领域是展示分类，不等同于关键词。

### 关键词配置

关键词用于关注、过滤或增强召回。

示例：

- 公司名。
- 产品名。
- 城市名。
- 政策名。
- 行业词。

后续可以支持用户配置关注关键词，但 v0.3 阶段建议先使用系统默认关键词或配置文件，避免前端配置能力过早扩大工程范围。

## 热度评分边界

热度评分必须可解释，而不是追求表面精确。

### 平台内热度

平台内热度基于该平台可获取指标计算。

可能使用的指标包括：

- 排名。
- 阅读量。
- 评论数。
- 点赞数。
- 转发数。
- 弹幕数。
- 收藏数。
- 报道数量。

不同平台字段不一致时，缺失字段应标记为 `unknown`，不应伪造成真实数值。

### 跨平台热度

跨平台热度不能直接比较原始数值。微博评论数、B 站播放量、知乎回答数和新闻报道数量不是同一量纲。

因此跨平台评分应采用：

- 平台内归一化。
- 基准线归一化。
- 评分明细保留。
- 综合分仅作为排序信号。

系统不应输出类似“某事件全网绝对最热”的强断言，除非有足够覆盖范围和来源依据。

### 评分解释

每个事件评分应保留 `score_detail_json`，至少说明：

- 使用了哪些平台信号。
- 哪些字段缺失。
- 官方报道强度。
- 社区讨论强度。
- 走势状态。
- 综合分来源。

## 数据质量与合规边界

第一阶段最重要的风险来自数据质量，而不是模型能力。

需要显式处理的问题包括：

- 平台字段不一致。
- 数据源更新频率不同。
- 社区平台采集稳定性不足。
- 热度指标不可直接横向比较。
- 同一事件在不同平台标题差异较大。
- 单一社区来源容易产生事实误判。

公开项目中不应包含：

- 账号、Cookie、Token 或私有配置。
- 过细的平台绕过策略。
- 未脱敏的原始样本。
- 不适合公开的采集失败细节。
- 可能引发合规争议的数据。

系统输出必须保留来源引用，并对低置信度内容使用不确定性表达。

## Guardrails 要求

两种模式都必须经过 Guardrails。

基础规则包括：

- 没有来源链接的内容不能进入正式简报。
- 单一社区来源不能写成确定事实。
- 低置信度事件合并必须进入人工确认。
- 核心实体冲突时禁止自动合并。
- 时间窗口冲突时禁止自动合并。
- 高风险判断必须保留不确定性提示。
- 每条事件卡片必须保留来源引用。

模式 B 还需要额外规则：

- 弱匹配不能作为确定结果返回。
- 证据不足时必须提示覆盖不足。
- 用户查询结果不能编造未入库来源。

## Evaluation 要求

产品模式设计需要能够被评估。

模式 A 的评估指标包括：

- 工具调用成功率。
- 字段完整率。
- 事件合并准确率。
- 日报重复率。
- 来源覆盖率。
- Guardrail violation 数量。
- 人工确认比例。

模式 B 的预留评估指标包括：

- 查询命中率。
- 强匹配准确率。
- 弱匹配误报率。
- 无匹配时的正确降级率。
- 返回结果来源覆盖率。

v0.3 阶段优先实现模式 A 的评估闭环，模式 B 只保留指标定义和后续评测入口。

## v0.3 范围

v0.3 完整交付：

- 模式 A：一图流热点简报。
- 默认平台和默认领域配置。
- 标准化数据结构。
- 事件抽取与合并。
- 热度评分。
- 每日简报结构化输出。
- 首页展示。
- 长图导出。
- Guardrails。
- Evaluation。
- Agent Ops 可观测性。

v0.3 预留：

- 模式 B：指定事件搜索输入框。
- `event_query` schema。
- `event_queries` 表。
- `retrieved_evidence` schema。
- `search_existing_evidence` 工具占位。
- 基于已有数据的最小检索结果。

v0.3 不实现：

- 完整 RAG。
- embedding 检索。
- 向量数据库。
- 多轮自主搜索 agent。
- 自动定向深度采集。
- 大规模评论抓取。
- 高反爬平台深度采集。

## 后续路线

模式 B 建议作为 v0.4 的重点。

优先扩展顺序：

```text
关键词检索 + 时间过滤
-> SQLite FTS5 / BM25
-> embedding 检索
-> 向量数据库
-> 多轮搜索 agent
```

只有当模式 A 的采集、事件合并、评分和来源证据足够稳定后，才适合扩展模式 B 的完整搜索能力。

## 对外表述

推荐对外描述为：

> 一个 workflow-driven agent system。系统通过 Planning 和 Tool Calling 编排新闻采集、社区信号分析、事件合并、热度评分和每日简报生成；第一阶段交付一图流热点简报，第二阶段基于同一事件证据库扩展指定事件搜索，并通过 Structured Output、Guardrails、Human Review 和 Evaluation 保证输出可追踪、可解释、可评估。
