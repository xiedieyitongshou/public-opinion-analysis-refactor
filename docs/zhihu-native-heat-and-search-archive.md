# 知乎原生热度与搜索增强封存

## 修改方案（2026-10-30）

常规采集不再用知乎热榜标题进行关键词搜索。保留搜索客户端、采集器、显式目标查询及历史记录，便于后续评估；不清空已有数据库，不重算旧简报。

当前本机 Docker 使用 `ZHIHU_HOT_LIST_PROVIDER=native`、`ZHIHU_SEARCH_ENRICHMENT_ENABLED=false`。原有官方开放平台模式仍可通过 `ZHIHU_HOT_LIST_PROVIDER=official` 使用；搜索默认关闭，只有显式启用旧开关后默认任务才重新安排搜索。

## 数据来源和边界

后端直接获取 `https://api.zhihu.com/topstory/hot-lists/total` 的 JSON，这是 RSSHub 知乎热榜路由使用的上游地址。现成 RSSHub `/zhihu/hot` 路由未输出热度，因此本实现不解析 RSS 文本，也不另外修改 RSSHub 镜像。

该地址是知乎客户端接口，不是已公开承诺稳定性的开发者 OpenAPI。请求不发送 Access Secret、浏览器 Cookie 或 CLI 授权信息。每轮一次请求，纳入 `zhihu_hot_list` 的请求计数；不自动重试，也不自动切换到付费搜索或 OpenAPI。

保存字段：问题 ID、原始标题和问题描述、列表排名、`detail_text` 热度原文、换算后的 `hot_value`、`answer_count`、`follower_count`、采集时间和原始条目。问题描述仍用于抽取、匹配和简介，不依赖搜索回答。

`3220 万热度` 换算为 `32,200,000`；这是展示值换算，不能宣称获得内部未舍入分数，也不是阅读量、点赞数或独立用户数。空值或无法识别的单位保留缺失，不补零。列表失败不推断事件离榜；无法识别条目导致列表不完整时，不用它证明其他事件不在榜。

## 热度与趋势

原生热度是知乎主热度依据。为兼容现有 0～1 接口，使用固定单调换算：

`platform_score = H / (H + 10,000,000)`

原始 H 及热度文本始终保留，简报展示原始“万热度”。不叠加样本赞评数、上榜次数、排名或合并条目数量；一个事件包含多个知乎问题时取最大热度，不累加。回答数、关注数作为辅助信息记录，不再次叠加到平台已有的综合热度。

原生热度缺失但排名有效时，降级为仅排名分并标明 `rank_only_fallback`，不冒充平台热度；接口失败则保留不可用状态。

连续两次完整且采样、计算版本可比的原生热度观测，按 `(H本轮-H前轮)/H前轮` 判断趋势，默认相对变化达到 5% 为升温／降温。前轮为 0 时不计算百分比，但正值增长可判升温。新旧热度口径、缺失与完整热度不混算趋势；不足两轮显示待确认。只在知乎内部比较，跨平台仍根据事件关联与各自排名展示。

## 日志与回退

沿用运行日志目录 `RUNTIME_LOG_DIR`。本机 Docker 映射为 `backend/data/resource-test/logs/YYYY-MM-DD/`，主服务写 `service.jsonl`，采集工作进程按现有 worker 文件名写入。默认保留14天。

- `zhihu_collection_policy`：启动及排队时记录来源模式与搜索开关。
- `zhihu_native_hotlist_fetched`：记录原始返回条数、选择条数、热度可用／缺失条数。
- `zhihu_native_hotlist_failed`：只记录异常类型和 HTTP 状态，不记录密钥或完整错误响应。
- `request_logs`：沿用逐请求计数，不伪装为调用官方开放平台付费额度。

人工回退时可将来源改为 `official`，重新创建后端容器；旧模式通常只有榜位，没有页面热度。不要为恢复热度而自动启用搜索。历史数据没有平台热度时不能用当前热度倒填过去时点。
