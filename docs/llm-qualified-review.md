# LLM 不确定候选分流

## 问题与方案（2026-10-30）

此前只要任意候选返回 `insufficient_evidence`，整条线索就可能送审；一个缺正文的无关候选也会阻挡另一个明确的同事件目标。当前新增结构化不确定原因及执行策略，仍由 LLM 判断语义，不恢复 embedding、reranker 或词典分数混合判断。

提示词版本为 `exclusive-events-v3`，执行策略为 `qualified-uncertainty-v1`。标题已经明确指向不同的主体、行为或讨论对象时，应直接判断不同，不能只因某侧没有正文而转待定。相同人物、行业、品牌、城市或“不能排除”不等于具体同事件线索。

## 输出契约

原有四种 `decision` 保持。`insufficient_evidence` 必须补充：

| uncertainty_kind | 含义 | 必需依据 |
| --- | --- | --- |
| possible_same_event | 有具体同事件线索，但缺少关键区分细节 | `same_event_clues` 必须包含双方逐字原文引用；`missing_information` 说明关键缺项 |
| insufficient_context | 材料不足，且没有具体同事件线索 | `same_event_clues=[]`，保留不确定判断和缺项 |

例如同型号车辆在同一城市发生相似事故，但缺少具体日期／地点，可判有线索待核实；“大体老师骨骼标本”与“菜鸟驿站转让”不应因缺正文而被视作潜在同事件目标。短品牌名或泛话题不能虚构成具体事件。

原引用、候选ID覆盖、JSON及Schema检查继续执行。新模型若遗漏不确定类型、编造引用、只提供单侧线索或没有关键缺项，进入技术异常处理，不自动合并。

## 后端处理

- 一个明确同事件目标，其他只有 `insufficient_context`：合并到明确目标。
- 多个明确同事件目标，或存在 `possible_same_event`：保留互斥归属约束，送人工复核。
- 没有明确匹配，也没有具体同事件线索：独立保留话题；原“不确定”仍完整保存在审计中，不改写为“不同事件”。弱信号发布保护仍生效，独立话题不等于已证实事实。
- 缺少新字段的旧响应：保守视为历史未分类不确定，保留审核，不能用“字段不存在”推断“没有线索”。
- 调用或校验失败：单列 `technical_error`，不展示为模型建议合并。保持不自动重试、不回退旧规则的策略。

前端将技术异常从批量归并选择中排除；人工仍可查看来源并作明确的单项处理，后台的人工归属与互斥校验继续生效。

`llm_detail.candidate_groups` 保存明确目标、具体关联待定、单纯上下文不足、历史未分类四组候选ID；全部逐对判断与引用继续保留。`review_category` 标记自动归并、独立话题、竞争目标、具体疑点、历史不确定或技术异常。

数值1.0／0.6／0.75是兼容现有接口的状态标记，不是LLM输出的同事件概率。LLM审核展示分类理由、具体关联线索与缺项，不再用未调用的embedding／reranker表格解释LLM判定。

## 版本、日志和历史边界

- 新提示词版本参与缓存键及采样签名，不直接复用旧响应；不同版本仍不混算热度趋势。
- `llm_review_policy` 运行日志仅记录线索ID、处理动作、分流类别和各组数量，失败只记录安全错误码，不写密钥、完整材料或供应商原始错误正文。
- 既有待审核记录和人工决定不自动改写；新策略作用于后续新比较。前端可识别旧记录中的调用失败并标为技术异常。
- 仅重启后端加载新版本，不自动开始新一轮采集、发送邮件或重新调用全部历史LLM任务。
